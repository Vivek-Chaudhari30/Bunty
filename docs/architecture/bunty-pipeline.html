How a person uses Bunty, end to end

A person in India saves one phone number. They WhatsApp it or call it, in Hindi, English, Hinglish or Gujarati. Behind that one number, every person has their own assistant with its own memory. Bunty does what they ask (reminders, calling or messaging someone, booking) and confirms when it is done. It never acts on the outside world without their "yes".

This page is what I understood from the repo (docs/architecture/, backend/router, integrations/, and Vellum's source). Correct anything that's wrong before we build.

The four ideas everything rests on

One assistant per personEach user gets their own Vellum assistant (decision D-01). Its owner is called the guardian.
Shared numbers, one routerOne WhatsApp number and one phone number for everyone. backend/router looks at the sender's number and passes the message or call to that person's assistant.
Vellum is the brainCalls, WhatsApp, voice-note transcription, memory, reminders and approvals are already in Vellum. We add plugins and setup, not a new brain.
Code checks the "yes"Anything outward (call, message, booking, money) needs the owner's approval, checked in code, not just asked for in the prompt.

Every inbound message or call hits the router first. Every outbound reply or call goes from the assistant straight to Meta or Twilio, without the router.

A user's journey, step by step

  1. Website · router

    Sign up not built

    They sign up on the website and prove the number with an OTP. Then two things happen: an assistant is created for them (hatch), and the router gets a row in users linking +910000000001 → chintu → https://chintu.<domain>. Consent for recording and data use is saved with a timestamp. The router endpoints for this exist (/internal/users, /internal/consent). The website form, the OTP provider (BUN-11) and automatic hatching (BUN-35) do not.

  2. Assistant

    Owner is recognized CLI, untested

    The assistant has to know this number is its owner, not a stranger. On calls, Vellum checks this with a six-digit code (guardian verification). On WhatsApp, assistant channel-verification-sessions create --channel whatsapp gives a code the owner sends from WhatsApp, with no code change. supportsVerification: false only affects what the app shows. Still to be tested live. Without it, the owner's own messages are refused as "unknown".

  3. User → Meta → router

    They send a WhatsApp router built

    "Kal subah 7 baje yaad dilana, dawai leni hai" as a voice note. Meta posts the webhook to the router. The router checks Meta's signature, finds the sender in users, and forwards the body unchanged with X-Hub-Signature-256, so the assistant's gateway can check the signature too. If one webhook holds messages from several people, the router splits it and re-signs each part.

  4. Gateway → daemon

    The assistant understands it Vellum built-in

    The gateway drops duplicate messages, downloads the voice note from Meta, and the daemon turns it into text before the model sees it. The model then reads memory (who the user is, their contacts, past requests) and picks a tool: a reminder, a call, a message, or a task for another person's assistant.

  5. Assistant → user

    It asks before acting in-chat buttons work notifications don't

    For anything outward ("Call Owner B and say 6 PM?") the tool is high-risk, so Vellum shows an approval prompt. In the owner's own WhatsApp chat these arrive as buttons like [Call] [Text instead], once the owner is verified on WhatsApp. But Vellum's notification system never sends to WhatsApp (deliveryEnabled: false). So questions raised in the middle of a call, access requests, and reminders don't reach WhatsApp. That needs a vellum/ change (V1 on the requirements page).

  6. Assistant → Twilio / Meta

    It does the task Vellum built-in our plugin built

    A reminder becomes a Vellum schedule. A call is placed with call_start through Twilio: the assistant says it is an AI calling for the user, talks with live speech-to-text and text-to-speech, and never calls emergency numbers. Our reach_contact tool decides between call, WhatsApp and the other person's assistant, then tells the router "I just contacted +91 …", so that person's replies come back here for 24 h.

  7. Assistant → user

    It confirms it's done text works voice reply not wired

    "Owner B ko call kiya, unhone OK bola." The reply goes as text. If the user sent a voice note, the plan is to reply with one too (decision D-07). The voice-reply code exists, but Vellum's WhatsApp sender can't send audio yet (BUN-44).

Path B: a phone call in detail

sequenceDiagram
  participant U as User's phone
  participant T as Twilio
  participant R as backend/router
  participant G as Chintu gateway
  participant D as Chintu daemon
  U->>T: dials shared number
  T->>R: POST /twilio/voice (X-Twilio-Signature)
  R->>R: check signature, rate limit (5/min), look up caller
  R-->>T: TwiML Redirect to chintu/webhooks/twilio/voice
  T->>G: POST /webhooks/twilio/voice (signed for this URL)
  G-->>T: Connect Stream
  T->>G: live audio over WebSocket
  G->>D: audio
  D->>D: Deepgram STT (language multi) → Claude → ElevenLabs TTS
  D->>T: spoken reply (barge-in supported)
  T->>U: hears answer

Why a redirect and not a proxy: Twilio's signature covers the URL. If Twilio calls the assistant itself, the signature stays valid and the audio never passes through the router.

The tricky part: one shared number

Messages to the shared number are routed by who sent them. Three cases:

Who writes or callsWhere it goesWhy
A user (in users)Their own assistantNormal case.
A non-user that an assistant contacted in the last 24 h (a shop, a friend)The assistant that contacted them (sticky_routes)So the clinic's reply reaches the user who asked Bunty to message the clinic.
Anyone elseOnboarding reply or short spoken message, then hang upNo assistant to send it to.
Owner A wants to reach Owner B, who is also a userAssistant to assistant (Chintu → Sujal), never shared-number WhatsAppOwner B's reply on the shared number would go to Sujal, not Chintu (decision D-05).

What worries me most

Two things. Meta's WhatsApp terms now ban "general-purpose AI assistants" (section 4.7), and Twilio can't give us an Indian number. Both are covered on the requirements page.

How I'd do the WhatsApp and phone work

From you or the team (blocking)

  • Anthropic API key (BUN-7)
  • Meta developer app, test number, 4 credentials (BUN-9). Business verification can take days, so start it first.
  • Twilio account and number, Deepgram and ElevenLabs keys (BUN-12)
  • Go / no-go on the 3 vellum/ changes (BUN-10)

Order I'd build and test in

  1. Hatch Chintu and Sujal locally, load our plugins (BUN-21, BUN-22).
  2. Public URL for each gateway (BUN-24). Point Meta straight at Chintu. Text, Hindi voice note, photo, PDF.
  3. The two vellum/ changes: owner on WhatsApp, approvals on WhatsApp (BUN-25, BUN-26). WhatsApp exit check (BUN-33).
  4. Twilio and India voices (BUN-27), phone verification (BUN-31). 10-call exit check under 2.5 s (BUN-42).
  5. Put the router in front of both. Two teammates, one number, each reaches their own assistant (BUN-32).
  6. Voice-note replies and first-contact templates (BUN-44, BUN-41).

Questions to check I've got it right

  1. One number or two? I assumed one shared WhatsApp number and one shared phone number for all users. Should they be the same Indian number, or is a Twilio number (often US or UK at first) fine for the prototype?
  2. Owner B's language. When Bunty calls a non-user, does it use the owner's language or detect the other person's? I assumed it detects (STT multi).
  3. Approvals on WhatsApp. OK to make the two small vellum/ changes (owner verification and approvals on WhatsApp)? Without them, WhatsApp-only users can't approve anything.
  4. Who are the first testers? I assumed only the three of us, on our own numbers, until the exit checks pass.
  5. Hosting for now. Local machines with tunnels for Phases 2 to 4, then one VM? Or straight to a VM?
